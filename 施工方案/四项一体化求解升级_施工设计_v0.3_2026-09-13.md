# 四项一体化求解升级：施工设计 v0.3

日期：2026-09-13。状态：四项首版已施工并完成本地联合验收，未启动新付费评测。实现边界与测试证据见 [受控搜索验收](../docs/acceptance/bounded-search-2026-09-13.md)。

本状态不等同于新题能力提升，也不表示已完成真实 DSH 对照。独立多采样是无 DSH 信息时的基线/消融，现有 `self_refine` 仍只称固定自查。

配套文件：[蓝图 v0.3](蓝图升级_v0.3_面向DeepSeek解题能力_2026-09-13.md)。本设计细化定点修复、工具辅助检查、多路线搜索和题内结构化记忆四项；四项联合验收后才算完整交付。

## 1. 总体决策

目标是让同一个 DS 在受限成本下，更有效地找解、选解与修补证明。现有研究工作台继续支持自由探索；新增可选的 `solver_controller=bounded_search_v1` 模式，在闭卷无人求解时管理路线、记忆和资源。

控制器是服务端确定性程序，负责状态、候选排序、派发和预算。数学路线、论证、缺口分析由 DS 提出。控制器不判断任意自然语言证明必然正确，也不为每次调度再调用一个“经理模型”。

四项的连接关系如下：多路线产生候选和局部成果；检查为候选提供有范围的证据；记忆保存版本、适用条件与缺口；控制器据此选择局部修复、继续推导或换路。最终提交只能引用实际保存的产物。

以下新增类名、字段和接口名均为拟定契约，不是现有实现声明。编码时允许改名，但不能删去约束和验收语义。

## 2. 先处理与现有代码的衔接

| 当前实现 | 接入决定 |
| --- | --- |
| `runtime/agent.py` 的 `AgentRuntime` 已管理步骤、子任务与研究操作 | 保留为执行层；新增控制器模块负责选择动作，不把搜索逻辑继续堆入整个类 |
| `runtime/service.py` 的 `claim_next` 按排队顺序领取任务 | 对受控根任务族先检查控制器派发资格；普通工作台任务保留现有行为 |
| `apply_step` 执行动作后按 `next_action` 自动继续或等待子任务 | 受控模式下 `next_action` 是建议，执行权由控制器决定；不能同时存在两套自动续跑逻辑 |
| `_spawn` 对研究和审查共用 `max_children`，父任务等待全部子任务结束 | 新增活动路线额度、任务族派发总上限和审查保留槽位；受控模式按相关事件唤醒，不能被已暂停备选路线永久挡住 |
| `initial_read_set` 自动纳入上下文和过去读取对象；`enrich_task` 拼接历史及子任务 | 受控模式改为固定的题目/路线/任务范围输入清单，防止再次把整个项目历史塞回上下文 |
| `runtime/context.py` 提供有哈希、有分页指针的压缩 | 保留并扩展到记忆包；重要假设被省略时必须显式阻塞依赖它的结论采用 |
| `Review`、研究对象、版本、证明方案和工具回执已有持久化 | 数学内容继续以这些记录为准；新增表只保存求解索引、调度状态和关系，避免双份“真理库” |
| 请求账本、租约、版本隔离、未知占用已有约束 | 所有受控动作走同一服务和账本，不能另开模型调用通道 |

特别注意：现有 `max_children` 限制的是累计子任务，不是同时工作的数量。仅把它设为三不能同时支持三条路线、多次局部修复和独立审查，必须拆分概念并保留任务族总上限。

## 3. 路线、任务与证明分别建模

### 3.1 路线是长期尝试，任务是一次具体工作

一个根求解会话对应一道题的一次独立试验。默认候选路线最多三条，活跃路线最多两条；同一路线允许多次推进、检查与修复，不能每次修复都创建一条新路线。

`SearchSession` 保存根任务、原题版本、算法版本、配置哈希、阶段、决策序号和预算配置。阶段为分析、搜索、核查、收尾、终止；阶段可以在搜索和核查之间返回，但进入收尾后不得再扩大探索。

`SearchRoute` 保存路线 ID、所属会话、原题版本、路线卡版本、工作分支、适用条件、核心归约、当前局部目标、候选产物、最近进展事件及修复历史索引。状态为待调度、执行中、待证据、待修复、暂停、有完整候选或关闭。

`RouteWork` 连接路线与现有 `AgentRun`/`Attempt`。工作类型包括推进、反例检查、独立审查、修复和组装。路线可以关联多个工作记录；每条路线同时最多一个会修改其数学材料的工作，审查读取固定快照。

关闭原因必须区分路线被具体证据否定、当前无进展、额度不足、用户停止和被新路线替代。关闭或暂停不等于证明该数学方法不可能成功。

### 3.2 路线分支按需创建

路线卡不立即复制整个项目。第一次执行路线工作时，基于同一个冻结题目快照创建工作分支；其他路线的后续修改不会自动进入它的输入。

首轮路线 Worker 不读取其他路线的解答、候选答案和自信评价。后续需要共享时，由显式导入记录带入某个引理版本及其假设，不进行整段对话广播。首轮共享原题分析仍会带来相关性，因此称“隔离首轮执行”，不声称严格独立采样。

同一证明方案中需要共同完成的子目标是共同前提；不同证明方案才是替代路线。不能把补齐两个必要引理的任务误当作“二选一”。共享引理记录供哪些证明方案使用，避免各路线重复证明同一已审查结果。

### 3.3 多样性检查

路线卡包含核心归约、关键引理、方法说明与廉价检验。格式化哈希只能识别完全相同的路线；语义相似由分析输出提供建议，初期不增加付费 embedding 或评分调用。

同一核心归约和同一关键引理的换词版本标记为疑似重复，默认不优先扩展。定义域、目标或假设不同的路线不自动合并；模型无法确认差异时保持待比较状态。允许随后证据推翻最初的去重判断。

独立多采样基线必须使用另一个模式：不共享首轮分析和中间引理，仅在终局按冻结规则聚合答案。这样才能测量搜索架构是否超越采样次数带来的收益。

## 4. 题内记忆：引用索引加任务输入包

### 4.1 记忆不是新的已证明事实库

`MemoryEntry` 存储会话、路线或共享范围、类型、源对象与版本、依赖版本、适用假设、来源事件和简短索引。类型至少包括定义/假设、候选引理、证明方案、实验观察、缺口和失败尝试。

证据维度单独保存：模型提出、自然语言审查未发现问题、有限范围实验、精确检查、经前提核对的精确反例。时效维度单独保存：当前、上游变化待重查、被替代、材料已删除。不能把这两个维度混成一个 `verified` 布尔值。

数学正文仍在 `Revision` 中，证据正文仍在 `Review` 或工具回执中。记忆索引可重建，不以自由文本摘要覆盖原文。假设下得到的结果只能条件性复用，不能因进入共享记忆而解除假设。

### 4.2 每次派发构建固定 `MemoryPacket`

按以下优先级选择内容：

1. 原题完整目标、变量范围和不可修改的约束。
2. 当前子目标及必要假设；本次实际选择的证明方案依赖闭包。
3. 本次要处理的缺口、相应原步骤和反例/审查依据。
4. 该路线最后一次有效检查点和最近的相关失败。
5. 明确导入的共享引理；其他路线只给简短状态索引。

首版使用关系与类型筛选，不以向量相似度决定是否能删除数学前提。对开放子目标可按结构关键词检索补充材料，但返回结果先是候选引用。

输入包记录条目 ID、版本、正文哈希、读入区间、未读内容及省略原因。接到现有 `Attempt.read_set` 和外部分支读集；仅在 checkpoint 里写一个列表而不接版本隔离是不够的。

必需材料超出上限时优先缩小任务或分步回读，不静默裁掉前提。省略索引也必须能完整分页取回，不能只保留前几十项而永久丢失入口。字符上限是工程限制，不能报告成精确 token 上限。

正式审查需要记录实际送达的完整目标及必要依赖。能按指针回读不等于已经读过；部分阅读只能给局部审查结论。Writer 有新的推导时要形成新版本并触发针对性检查。

### 4.3 更新、冲突与失效

一次工作结算后，只根据成功执行的动作回执更新记忆，拒绝把模型说“已经证明/已经运行”当作事实。重复应用同一请求回执不能生成重复记忆。

上游版本改变时，标记依赖旧版本的具体证明方案需重查。依赖图反向传播到使用该方案的工作和记忆包；独立替代方案不受此影响。纯文字改写也不自动迁移审查结论。

不同路线对同一命题产生冲突结论时，同时保存候选与各自证据，创建冲突缺口；无证据优势时优先检查争议的最小命题，不靠票数合并结论。

从旧快照返回的结果遵守既有隔离规则，不能直接合并到当前主线。可保留历史材料供显式再审使用，但不自动重新派发付费任务。已永久删除的材料连同摘要、路线卡中的派生正文、输入包、缓存和决策解释均纳入清理；预算数值账本继续保留。

跨分支导入必须固定来源分支和版本，并核对目标分支的上下文。源材料不能仅因在其他分支存在就被当前证明自动引用；需要按现有引用/合并机制建立可访问的引用闭包，且不把导入动作变成数学等价认证。

题内记忆严格限定 `project_id + root_run_id`；benchmark 再限定条件和重复编号。固定共享初始材料可以显式导入，但不同试验的解答、失败经验与评分反馈不能相互传递。

## 5. 缺口与修复合同

`GapRecord` 绑定被审查的证明版本、步骤锚点、涉及的前提、问题类别、证据引用、受影响方案和修复次数。步骤锚点使用该版本中的稳定段落/步骤 ID；没有 ID 时使用文本范围和哈希。修改之后需重新定位，不能把旧行号直接套到新证明。

问题类别至少区分算术/代数错误、缺少条件、量词错误、循环依赖、关键引理有反例、缺少论证和检查材料不足。由模型提出类别，服务端验证引用与来源，不声称能够自动确认所有数学分类。

`RepairContract` 明确要修的目标、可复用的局部成果、必须舍弃的推导、不得更改的原题条件、需要回应的反例及本次额度。它是路线内的一项工作，而不是“请从头再做一次”。

修复产物要明确替换哪些版本、留下什么缺口。服务端把受影响的后续依赖转为待重查；修复 Worker 不得给自己的新版本签发独立审查通过。

默认对相同版本和相同缺口安排一次修复。新证据或新的核心方案可以支持再次修复，但需记录变化，仍受路线和全局预算限制。缺口在独立检查后才转为“审查未发现原问题”或“指定范围精确检查通过”，不能用“文字改过了”关闭。

## 6. 工具检查如何真正接入搜索

工具不是每条路线的必经步骤。优先检查决定全局成败且可以廉价执行的局部命题，例如候选恒等式、整数边界、构造是否满足条件或疑似不等式反例。

`CheckRequest` 包含目标版本、被检查命题、输入范围、预期证据类型和执行上限。工具产生 `CheckResult`，保留代码、环境与输出引用、检查范围、前提核对结果及执行状态。

精确计算、浮点试验和程序错误分别记录。模型写的程序出错是工具程序失败，不是数学反例；浮点误差造成的疑似反例需要提高精度或精确复核；枚举未找到反例只为该有限检查提供观察。

证据进入控制器前分两关：执行是否完整有效，以及输入是否真正对应待检命题。后者可由确定性规则处理已支持的表达式，也可由独立 DS 检查题意映射；由模型核对的映射必须标明，并计入调用预算。形式化证明仍不实施。

优先复用当前精确计算器与标准库沙箱。新数学库是独立适配工作，需冻结版本并验收。不能为解决依赖问题绕过沙箱到宿主执行代码。

## 7. 控制器如何选择下一步

### 7.1 事件驱动，不等待所有路线结束

输入事件包括路线工作完成、证据返回、版本变化、工具失败、用户干预和额度变化。每个事件先校验归属与版本，再更新路线和记忆，最后只选一个或有限个可派发动作。

备选路线暂停不阻塞主线推进。候选有了重要结果，控制器可以立即安排检查；不需要等待所有子任务完成。其他已派发请求不假定能免费取消，仍计入在途占用。

### 7.2 排序规则先简单、可复现

每次先排除未授权、输入过期、重复在途、前提未齐、额度不足和已无修复机会的动作。剩余动作按以下规则选择：

1. 已达到收尾边界时，停止新探索，进入最终选择与提交。
2. 有具体反例或版本失效时，先隔离受影响方案；纯状态更新不消耗模型请求。
3. 对完整候选的关键缺口安排核查或一次局部修复。
4. 推进最近产生了可核查局部成果的路线。
5. 用预留探索机会推进尚未获得首轮试探的不同路线。
6. 所有候选都停滞时，在额度允许下激活备用路线，否则总结当前结果。

步骤三不能无限抢占：每个缺口有修复上限，每轮核查有额度上限。完整候选指有覆盖目标的候选论证，不表示已经正确。

进展信号采用向量：当前覆盖的明确子目标、未解决的关键缺口、证据类型、最近是否新增有效产物、重复尝试次数和已用成本。不同路线的子目标数量不可直接相加比较，拆成更多引理也不会获得更高分；第一版不输出“完成百分比”。

新路线首轮试探机会与最终预留冲突时，以硬预算为准并记录未获试探原因。相同优先级按固定创建序号打破平局，便于回放；如测试随机策略，种子写入配置。

### 7.3 保留替代路线，不把失败变成全局否定

一条路线被反例击中，其他不依赖该步骤的路线仍可继续。某个共享引理失败，则所有使用该引理版本的方案待重查。已获得的不同方法候选可保留用于最终比较，但不能使用答案键决定选择。

最终候选排序优先排除有未处理反证的候选，其次比较目标覆盖、显式缺口和证据范围。模型自信与候选票数仅作辅助信息；无法分辨时可以提交带不确定性的答案或弃答，具体取决于答案模式或研究模式。

## 8. 预算与运行保护

### 8.1 资源分为不同约束

会话总请求数、累计输出上限、并发数、工具执行额度、墙钟期限均独立控制。旧 `max_children` 不可作为全部资源约束的替代。

调度器在同一数据库事务中校验额度、登记决策与工作、预留派发资格。服务端实际 `reserve_request` 再原子校验并预留输出；任务派发额度与真实请求占用采用转换关系，不能双重扣除，也不能在两者之间出现可超额的空窗。

修复、审查与收尾额度是受保护容量，不是已经计费的请求。真正派发后才写入真实请求账本；调度日志和费用账本分别保留。探索不能借用收尾容量。未用审查额度只能在满足既定条件后转给核查或收尾，不能被模型自行转回探索。

### 8.2 八请求示例，仅用于说明设计

| 用途 | 请求槽位 | 说明 |
| --- | --- | --- |
| 合并分析与路线规划 | 一次 | 提出路线并确定各自局部目标 |
| 两条路线首轮推进 | 两次 | 每条一次；不要求两条都写完整长证明 |
| 候选独立审查 | 一次 | 检查选定版本及其关键依赖 |
| 局部修复 | 一次 | 无缺口时可释放给核查或收尾 |
| 修复后复查 | 一次 | 防止原缺口换成另一个未经检查的新步骤 |
| 最终提交 | 一次 | 受保护的根任务收尾步骤 |
| 故障或额外推进机动 | 一次 | 协议恢复也从这里或对应阶段余额扣减 |

这是可调整配置，不承诺八次足够解决难题。若累计输出额度为 \(32768\)，可先以探索 \(16384\)、核查/修复 \(12288\)、最终提交 \(4096\) 作为开发实例；单次上限、实际剩余量与在途预留共同限制派发。机动请求没有额外 token，总和仍不得超过 \(32768\)。

极小预算下合并规划和首轮求解，减少活跃路线；功能仍存在，但不强行运行全部环节。启动前检查请求、步数、子任务和输出容量是否足以满足所选完成策略；不满足则明确报告配置不足，或采用用户预先选定的较轻模式，不能偷偷降低证明标准。

原子预算保护同时覆盖格式恢复和未知续试。最终请求若结果未知，保留占用并按现有整棵任务族最多一次的策略处理；没有余量时停止，不能保证总能拿到最终答案。

墙钟临近期限时停止新搜索并保留可配置收尾时间。已经在途的调用可能超出估计时间，必须明确记录实际延迟，不伪称硬性保证供应商响应。

## 9. 状态一致性、恢复与人工干预

`SearchDecision` 保存会话序号、触发事件 ID、所读路线版本、记忆包哈希、候选动作、选择理由、预算快照和关联执行 ID。相同事件重复送达时返回同一决策，不重复派发。

使用会话版本比较更新防止两个调度循环同时选中同一槽位。路线状态迁移、工作登记和派发资格在一个事务内完成；可重复读取的派发记录用于进程崩溃恢复。执行请求仍受现有租约和幂等机制约束。

逻辑工作幂等键包含会话、路线、动作种类、输入快照、缺口和本次获准尝试序号；事件重复不会新增序号。合法的再次试探必须显式登记为新尝试，避免一方面重复执行旧动作，另一方面把真正获准的后续尝试永久拒绝。

恢复顺序：先核对在途请求和已保存的结果，再补应用尚未应用的有效回执，最后选择下一步。不能因为控制器进程重启就重跑旧请求；未知请求不得当作空闲槽位。

用户暂停整个会话时保留所有路线检查点；暂停一条路线只影响该路线及相关在途工作。修改原题或关键条件时递增控制版本，原快照迟到结果隔离。用户改主线优先级可以影响后续调度，但不能把未经审查候选改成已证明。

## 10. 接口与配置边界

候选操作为 `propose_routes`、`report_progress`、`report_gap`、`propose_check` 和 `request_memory`。参数引用必须属于本次输入或服务端返回的实际回执；模型不能构造跨会话 ID。

受控模式下，模型的 `spawn_task`、`request_review` 和工具请求都经过控制器的资格和额度检查。不能通过旧操作接口或直接领取子任务绕开调度。非受控模式保持现有权限和行为。

建议新增会话状态、路线详情、记忆目录、缺口、决策记录的只读 API，以及沿用权限检查的路线暂停/恢复/优先级操作。默认页面只显示当前目标、主路线、备选路线、关键缺口和下一步理由；技术日志放在展开区。

配置包含控制器版本、候选数、活跃路线数、修复上限、额度池、上下文上限及实验开关。会话启动时冻结配置，进行中的用户改动写成新控制事件。主评测默认禁止人工变更；发生变更标记为有人干预。

旧任务保持 legacy 模式，不根据历史文本猜测并补写“过去采用过的路线”。需要继续旧项目时，显式创建新的受控会话并记录导入材料；历史批次、费用和评分保持原样。新模式默认不改变既有 runner 的行为，须显式选用并写入冻结配置。

## 12. 验收矩阵

| 场景 | 应观察到的结果 |
| --- | --- |
| 第一条路线关键引理被反例否定，第二条不依赖它 | 第一条停止该方案，第二条继续，原题不被宣布错误 |
| 两条路线共享引理，但假设范围不同 | 导入时保留假设差异，不能直接共享无条件结论 |
| 两个必要子目标只完成一个 | 仍有明确缺口，不能作为替代路线提前完成 |
| 一处局部错误，其余成果可独立复用 | 生成定点修复合同，保留不依赖错误的成果 |
| 修复改了原题量词或强化假设 | 不视为原任务完成，保留条件变化记录 |
| 工具没有发现有限范围反例 | 记录观察，不能升格为无限范围证明 |
| 浮点伪反例、程序错误、题意映射错误 | 不撤回数学命题，产生正确的检查状态与后续任务 |
| 原证明版本更新 | 旧审查不迁移，新版本与受影响方案待重查 |
| 输入包压缩遗漏关键前提 | 可完整回读；读取不足不满足相应审查采用要求 |
| 备选路线暂停，主路线已有候选 | 主路线能进入核查/收尾，不被等待全部子任务卡住 |
| 两个调度器同时处理同一事件 | 仅生成一次有效派发，额度不重复占用 |
| 进程在预留、派发、结算、应用回执之间崩溃 | 恢复后账本和路线一致，不重复付费请求 |
| 探索与协议恢复消耗全部可用探索资源 | 最终请求槽和输出仍受到保护，不能被子任务抢走 |
| 未知请求续试 | 旧占用保留，整棵任务族至多一次，所有路线共享此限制 |
| 永久删除材料后迟到结果返回 | 路线摘要/记忆/输入包不复活正文，费用记录仍在 |
| 不同题目、条件或重复编号 | 无解答和失败经验串用，评分反馈仅在离线评估端 |

使用合成任务与 mock 推理验证状态机制，真实沙箱验证隔离和证据记录。合成模型按输入合同生成有区别的响应，不能只按固定轮数输出成功；至少包含新缺陷变体、无解候选、错误审查和持续无进展场景。测试通过只说明机制工作，不证明 DS 数学能力提高。

## 13. 一次完整闭环应该怎样运行

以下是行为示例，不是按轮次写死的成功剧本，也不提供任何评测题的答案。

1. 分析提出路线甲和路线乙。甲把目标归约到一个关键引理；乙使用不同构造。两者基于同一原题，分别执行首轮局部工作。
2. 甲保存关键引理的候选证明及一个不依赖该引理的辅助结果；乙保存构造和一个边界缺口。服务端保存真实版本，记忆索引分别记录适用条件。
3. 甲的候选接近形成完整论证，控制器安排检查。检查发现关键引理在其声称范围内有反例；辅助结果不依赖这一步，因此仍可供显式复用。
4. 缺口记录指向甲的具体步骤，甲的相关证明方案转为待修复。控制器检查修复额度与已尝试次数，派发替代引理任务。若它仅重复原说法，记录无进展并暂停甲，不循环重写整篇证明。
5. 乙继续处理自己的边界缺口。如果甲的辅助结果适用，乙通过固定版本导入；否则仍独立推进，不因为甲失败就丢弃乙。
6. 乙形成候选后进入独立审查。收尾前停止新探索，将已选择候选、证据范围和未决问题交给根任务正式提交。若两条路线都未完成，答案模式可提交明确候选并标注证明缺口，研究模式报告未解决。

这条链路的验收关键是：**错误确实改变后续行动、有效成果确实被保留、另一条路线确实能继续、每一步确实受同一预算约束。** 只在日志中出现“多路线”“记忆”“修复”等词不能算实现。

## 14. 能力评测与完成边界

四项功能联合完成后，再进行付费开发试验和冻结留出比较。仍沿用蓝图中的同底模、同工具、实际成本报告和外部证明盲评要求。

完整系统分别关闭定点修复、工具辅助检查、主动多路线或任务相关记忆选择，观察增量。关闭记忆选择时仍保留不可变记录、必要前提与审查完整性，不能为了消融故意丢掉正确性保护；改用统一预算内的基础上下文策略。关闭多路线时仍使用相同预算允许单路线继续修订。未花完额度也如实报告，不故意烧满预算。

对真实 DSH 仍需确定指定实现。新增多采样基线与本系统不能依靠金标准选候选。报告候选覆盖、最终选择、修复成功、错误接受、缺答、成本与时间，区别“更会找解”与“更会挑选或提交已有解”。

工程完成的条件是四项全部接通并通过联合验收；能力提升的条件是冻结后的新题对照支持收益。若某个模块在特定预算下无益，可以通过配置关闭，但不能以实验尚未证明收益为由省略本次明确要求的功能实现。

## 15. 当前实现差异附录（2026-09-13）

本附录记录已接通代码与施工设计的差异，不把设计意图当作验收事实。

- 会话阶段为 `analysis/search/final/terminated`，核查与修复分别使用 `check/repair` 工作，共用检查额度池。调度按候选核查、缺口修复、首轮机会、人工优先级和创建序号确定，不采用学习评分器。
- 路线最多三条、活跃路线最多两条，重复判断采用 `core_reduction`、`key_lemmas`、`assumptions` 的确定性精确哈希。模型还可标记疑似重复及原因；同假设的疑似重复降优先级，不自动合并或认证数学等价。
- 缺口、候选选择、修复内容和工具适用条件由模型提出；服务端执行 schema、版本、权限、证据引用和预算校验，不把模型语义判断改写成形式化证明。
- 题内记忆已按搜索会话和路线保存、分页并返回版本引用；摘要压缩会留下回读指针。跨题自学习、自动跨条件迁移和知识库冻结对照仍需独立事实验收。
- 四个运行开关是定点修复、工具检查、题内记忆和多路线；关闭某项时仍保留版本、预算和安全校验。开关收益尚无付费盲测证据。
- UI 可在“启动研究→求解控制器”选择 `bounded_search_v1`；默认仍为 `legacy`。CLI 通过 `--solver-controller` 和 `--search-config` 选择，配置在启动时冻结。

本地 API、真实 Docker 隔离、浏览器及定点修复后复验的计数已归档，人工路线操作纳入无人评测审计。后续仍需冻结留出题上的成本匹配对照、指定 DSH 的版本与提示契约，以及外部证明盲评分；这些证据具备前，不得声称本升级提高了 DeepSeek 解题能力。
